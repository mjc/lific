Lific's MCP server is part of the same binary as the web UI and the REST API, and it reads and writes the same database. An agent connected over MCP can create and triage issues, write pages, keep plans, comment, search, read the activity log and handle attachments. The [tool reference](/docs/mcp/tools) documents all 31 tools, and [Working with Lific as an agent](/docs/mcp/agents) covers the conventions to know before the first call.

The short version:

- The HTTP endpoint, `https://your-server.example/mcp`, authenticates every request with a bearer API key or an OAuth 2.1 access token.
- Local stdio, `lific mcp`, has no transport authentication. The agent's identity is the API key in `LIFIC_TOKEN`, checked again before every tool call.
- Remote stdio, `lific mcp --remote --url <BASE_URL>`, is a local command that forwards to a server's HTTP endpoint with a bearer credential.
- A tool that cannot do what you asked returns `isError: true` with text starting with `Error:`. A parameter the tool does not declare is refused before it runs, with a suggestion for the name you probably meant.
- Lists are paged. When more rows exist, the output ends with the `offset` to pass on the next call.
- July 2026 clients use `server/discover` and per-request metadata, with no initialization handshake. Legacy clients use `initialize` and `notifications/initialized`.

Most people never configure this by hand. [`lific connect`](/docs/connect) detects your AI tools and writes one of these setups for each. This page describes what it writes, and what to write yourself when it does not cover your client.

## Pick a transport

| Transport | The client runs or opens | Authentication | Needs a running server |
| --- | --- | --- | --- |
| HTTP | `https://your-server.example/mcp` | Bearer API key or OAuth 2.1, on every request. | Yes |
| Local stdio | `lific mcp`, which opens the database file directly. | None at the transport. Identity comes from `LIFIC_TOKEN`. | No |
| Remote stdio | `lific mcp --remote --url <BASE_URL>`, which forwards each request to `<BASE_URL>/mcp`. | `--api-key` or `LIFIC_API_KEY`, else the credential `lific login` stored for that URL. | Yes |
| Multi-instance stdio | `lific mcp --instances <FILE>`, in front of several servers. | One credential per alias. See [Multi-instance MCP](/docs/mcp/multi-instance). | Yes, each one |

Both single-server stdio forms resolve a [repository binding](/docs/repository-bindings) from the directory the client launches them in, so a few project-scoped tools can omit `project`. A direct HTTP connection has no checkout to inspect and never infers a project. The [tool reference](/docs/mcp/tools#which-tools-use-a-repository-binding) lists the tools that use a binding.

The server advertises the tools capability only. It serves no MCP resources or prompts on any transport.

## HTTP endpoint

```text
https://your-server.example/mcp
```

The endpoint supports MCP `2026-07-28` plus legacy `2025-03-26`, `2025-06-18` and `2025-11-25`. July requests are stateless: every request carries `_meta` with `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities`, plus `MCP-Protocol-Version` and `Mcp-Method` HTTP headers. Calls to named tools also carry `Mcp-Name`. `server/discover` returns the supported versions, capabilities and instructions without initialization. Results carry `resultType: "complete"`.

Legacy clients perform `initialize`, retain the returned `Mcp-Session-Id`, and send `notifications/initialized`. Subsequent requests include the session ID; June and November clients also include the negotiated `MCP-Protocol-Version`. March clients can omit that version header. HTTP responses can be JSON or SSE; clients must accept both. Unsupported legacy initialization versions negotiate November 2025.

March sessions receive JSON-RPC batches over HTTP and stdio, including the remote and multi-instance proxies. Initialize with an individual request first. Batch replies preserve request IDs and omit notifications; an empty batch or a batched initialization is invalid. June, November and July requests use individual messages.

A batch may contain at most 1,024 members. HTTP batch input and all stdio input frames, including individual requests, are capped at 1 MiB; combined batch replies are capped at 4 MiB. Remote batch exchanges share a 120-second network budget. HTTP batch replies have a separate 30-second delivery grace after processing finishes; completed results remain available during that grace, then unread output is discarded.

Legacy HTTP allows up to 1,024 non-cancelled outstanding requests across sessions, with a shared 4 MiB cap on their session-ID plus serialized request-ID bytes. A legacy session retains cancelled request IDs until it closes, preventing late replies from being attributed to a reused ID. Each HTTP session allows 1,024 outstanding or cancelled IDs and 4 MiB of session-ID plus serialized request-ID bytes; each local stdio session allows 1,024 outstanding or cancelled IDs and 4 MiB of serialized request-ID bytes. Reconnect if a session reaches either per-session limit. A session with 1,024 non-cancelled requests uses all shared HTTP request slots; cancelled IDs do not count against the shared request or identifier-byte limits.

Concurrent explicit cancellation over HTTP or local stdio omits the cancelled member while remaining replies complete. Remote and multi-instance proxies retain their serial request processing: a cancellation cannot interrupt a call already being forwarded.

If a remote or multi-instance batch exhausts its output budget, earlier completed replies are retained. Later calls receive errors without being forwarded; notifications receive no replies. The proxy continues accepting subsequent requests.

Requests with an `Origin` header must match `server.cors_origins`, the public server origin, or a local loopback origin. Other origins receive HTTP 403. Configured browser origins remain specific to their scheme, host and port.

A request must carry a `Host` the server recognizes, as a guard against DNS rebinding: `localhost`, `127.0.0.1`, `::1`, or the hostname of `server.public_url` when that is set. Behind a reverse proxy, set [`server.public_url`](/docs/configuration) to the address agents use, or requests are refused with `403 Forbidden: Host header is not allowed`.

### API key

Create a key with `lific key create --name <NAME>`, or from **Connected Tools** in the web UI. The plaintext value is shown once. Send it as a bearer token:

```json
{
  "mcpServers": {
    "lific": {
      "type": "http",
      "url": "https://your-server.example/mcp",
      "headers": {
        "Authorization": "Bearer <API_KEY>"
      }
    }
  }
}
```

Field names differ between clients. `lific connect` knows each one's shape; see [Connect agents](/docs/connect).

### OAuth 2.1

An OAuth-capable client can connect to the endpoint URL with no credential and run the flow itself. A request with no credential gets `401` with a `WWW-Authenticate` header pointing at the protected-resource metadata, `/.well-known/oauth-protected-resource/mcp`. Authorization-server metadata is at `/.well-known/oauth-authorization-server`.

Lific supports the authorization-code grant with S256 PKCE and the device authorization grant, and implements dynamic client registration at `/oauth/register`. A registered redirect URI must be an absolute `http` or `https` URL. Lific issues no client secrets, so the only token endpoint authentication method it advertises is `none`. Client ID Metadata Documents are not yet supported; clients can use dynamic registration or a pre-registered client.

New authorization and device grants retain their canonical resource through token exchange. A token request for another resource is rejected, and issued tokens are checked against their resource on HTTP requests. Existing grants and tokens without resource metadata remain compatible until they expire. Native clients registered with `application_type: "native"` may change the port of a loopback IP callback; all other redirect components must match exactly.

New device token requests must include the client ID used to request that device code. An omitted or different client ID is rejected without consuming the approved grant. Pending grants created before the upgrade still accept an omitted client ID until they expire; a supplied different ID is rejected.

Both grants are approved from a signed-in browser, and only from a browser: an OAuth access token cannot approve an authorization request or a device code. The browser session must also have signed in within the last 15 minutes, because approving a connection mints a 30-day credential for the tool.

An older session is refused, and the refusal is not resumed for you. Nothing is created. To continue, sign **out** of Lific (revisiting the login page does not help, since the old session is still valid, just old), sign back in, then start the connection again from your client. On an instance that signs in without a password, signing out and reloading is enough.

Approval binds the grant to a per-tool bot owned by the approving human, and the token exchange is refused unless the grant names an identity that may still authenticate. A grant that names nobody returns `invalid_grant`; so does one whose bot was deleted, whose owner was deactivated, or whose owner ran an account recovery between approval and exchange.

### Other ways in

With `[auth] required = false`, a request that carries no credential runs as the operator. A request that carries an invalid credential is still refused. [Self-hosting](/docs/self-hosting#authentication) explains when Lific refuses to start in that mode.

If `server.mcp_path_token` is set, `/mcp/<token>` accepts MCP requests with no other authentication. The path is the credential. It exists for clients whose OAuth flow is broken.

## Local stdio and `LIFIC_TOKEN`

A local stdio session has no transport authentication. Whoever can launch the process can talk to it, so the launch is the trust boundary. The session's identity is the `LIFIC_TOKEN` environment variable, which holds an API key, the same credential the HTTP transport accepts. `lific connect --stdio` writes it into the client's configuration entry.

Lific checks it once at startup:

- Absent, or valid but not bound to a user: the session runs as the operator, and Lific prints a warning to standard error.
- Present and valid: the session runs as that agent.
- Present but invalid, for example revoked or mistyped: Lific refuses to start. A bad agent credential must not fall back to operator access.

### Revocation takes effect at the next tool call

The startup check is a fail-fast, not the enforcement point. A stdio session can run for days, so Lific resolves `LIFIC_TOKEN` against the database again before **every** tool call and takes the caller's identity from that check. Revoking the key, changing the owner's password, signing out everywhere, or deactivating the account stops the agent at its next call. The tool never runs, so nothing is written.

The refusal is a tool result flagged `isError: true`, not a JSON-RPC protocol error, because the request was well formed and the session is still usable. The text tells the agent to run `lific connect` and restart the MCP server. It does not say why the credential failed; that goes to the server's log.

A session launched with no `LIFIC_TOKEN` has no credential to check and keeps its operator behavior.

`LIFIC_TOKEN` is not `LIFIC_API_KEY`. `LIFIC_API_KEY` is the bearer credential for HTTP access, read by remote stdio, Codex and `lific doctor`. See [Connect agents](/docs/connect#lific_api_key-and-lific_token).

### Discovery and legacy initialization

July requests carry the same per-request metadata over stdio as HTTP. Discovery and tool calls need no initialization. Legacy clients retain the initialization handshake; the server negotiates March, June or November 2025 and omits `resultType: "complete"` from their responses.

## Remote stdio

`lific mcp --remote --url https://your-server.example` gives a client that only launches commands a way to reach a server. It opens no database. Each request is POSTed to the server's `/mcp` endpoint with the credential, so authentication and revocation work exactly as they do over HTTP. `LIFIC_URL` can stand in for `--url`.

The proxy preserves JSON-RPC errors returned by the server. When the server is unreachable, answers with a transport error, or rejects the credential, the proxy answers that request with a JSON-RPC error (`-32603`) carrying a readable message, and keeps running. It ends only when the client closes its input. The [remote stdio walkthrough](/docs/repository-bindings#use-a-remote-server) covers binding a checkout through it.

If the server explicitly rejects an expired legacy session, the proxy completes a fresh handshake and retries the rejected request once. Recovery uses the same server and credential, retains the negotiated protocol version, and shares the original request's 120-second HTTP timeout. Authentication failures, tool errors and protocol errors are returned without retrying the call.

## Response conventions

These hold on every transport.

### Failures are text

A tool that cannot do what you asked returns an ordinary result whose text starts with `Error:`, followed by what went wrong: an unknown identifier, a missing role, an ambiguous edit, a stale `expected_seq`. It has `isError: true`, so read the text and correct the call. Database and internal faults are reported only as `Error: internal server error`; the detail goes to the server log.

Argument validation failures also return `isError: true`, so an agent can correct and retry its call:

- Arguments that do not fit the tool's schema return a tool error: a missing required parameter, a wrong type, or a parameter the tool does not declare. Unknown parameters are refused on every tool, nested objects included, so a misspelling cannot quietly change the answer. The message names the unknown key, suggests the closest valid name, and lists the valid ones, for example ``Unknown parameter `comments` in get_issue. Did you mean `include_comments`?``

JSON-RPC errors describe malformed protocol requests and unknown tools. The remote stdio proxy returns `-32603` when it cannot reach the server. Multi-instance selection errors are tool errors for July clients and `-32602` errors for legacy clients.

A revoked stdio credential is also flagged `isError: true`. An unrecognized `resource_type` or `action` in `list_resources`, `manage_resource` or `delete` returns a line naming the accepted values.

### Lists are paged

`list_issues`, `list_comments`, `search`, `get_activity`, and `list_resources` for issues and pages return one page. When more rows exist, the output ends with a line naming the `offset` to pass next, such as `call again with offset=50`. Pass it back with the same filters. `get_attachment` pages a text file the same way, by line, and `export` pages a whole project by document. A `get_page` read cut at its size budget ends with the exact call, `offset` included, that continues it.

The plan listing in `list_resources` honors `limit` and `offset` but prints no hint, and `list_attachments` is not paged. The [agent guide](/docs/mcp/agents#page-through-lists) lists each tool's default and cap.

### Responses are bounded

Agent harnesses cut long tool output off without saying so, so the tools that can return a lot hold themselves to a budget and say when they hit it:

| Tool | Budget | When it is reached |
| --- | --- | --- |
| `get_issue`, `list_comments` | 2 MiB | Fewer comments are returned, and the output says the size budget, not the row limit, ended the page. |
| `get_page` | 30,000 characters of content | A long page returns its outline and opening; read the rest by `section` or `offset`. |
| `get_briefing` | 6,000 characters | Lines are dropped from the longest sections, and each cut section names the call that lists everything. |
| `export` for a project | 256 KiB of Markdown | The page of documents stops early, and the last line gives the next `offset`. |

## Identity and authorization

MCP resolves the caller exactly as REST does, in every auth mode. An agent cannot do more through MCP than the same account can do through the web UI, and both surfaces check the same roles.

Writes by a connected agent are attributed to that agent in the [activity log](/docs/concepts/comments-and-activity#activity-log), not to the operator who connected it, and each entry records `mcp` as the transport. `lific connect` and OAuth approval each mint a per-tool bot for this, so a tool acts as itself and inherits its owner's project access.

## Registry manifest

The repository ships an MCP Registry manifest in `server.json`. It declares the Cargo package `lific` and a stdio launch command of `lific mcp`. The manifest describes the stdio package transport only; it configures no HTTP endpoint.
